# PitMetric Core Domain Architecture

## Goal

PitMetric must preserve a technically correct history of what was installed on a vehicle, how it was used, and why a component accumulated a given amount of use. The domain must not assume that every component is measured only in kilometres.

## Core concepts

### Vehicle
A physical kart, car or other competition vehicle.

### Configuration
A logical build of the vehicle: which physical components are installed together.

A configuration is not the same as a technical setup. Configuration means hardware composition; Setup means adjustable values such as tyre pressure, camber, toe, gearing or ride height.

### ConfigurationVersion
An immutable historical snapshot of a Configuration.

Once a version has been used by a finalized Session it must never be edited in place. Changing a component creates a new ConfigurationVersion.

Example:

- Race Build V1: Engine A, Chain B, Tyres C
- Session 10 references V1
- Engine A is replaced
- Race Build V2: Engine D, Chain B, Tyres C
- Session 11 references V2

Session 10 must always continue to show Engine A.

### ComponentType and Component
ComponentType describes a class such as Engine, Chain, Tyres or Brake Pads. Component represents a real physical instance such as `Rotax Engine #02` or `Tyre Set #07`.

### UsageMetricType
Usage is metric-agnostic. Initial system metrics are:

- distance
- runtime
- cycles
- sessions
- events

Distance should be stored in metres, runtime in seconds, and counter-like metrics as integers. Display units are presentation concerns.

### ComponentTracker
A component can track zero or more metrics. An engine may track distance and runtime; a chain only distance; tyres distance and heat cycles.

### Session
A track session references a specific ConfigurationVersion and optionally a SetupVersion and CircuitLayout. Finalizing a session calculates the usage generated by that session.

### Usage ledger
Usage is stored as append-only entries instead of mutable lifetime counters. A session that produces 50 km and 3,000 seconds creates usage entries against compatible trackers of every component in the selected configuration snapshot.

The historical ledger is the source of truth. Cached totals may be added later for performance.

## Session finalization

A future `FinalizeSessionService` should run in one database transaction:

1. lock the draft Session;
2. validate that it has not already been finalized;
3. resolve its immutable ConfigurationVersion;
4. calculate session metrics server-side;
5. create UsageBatch records for generated metrics;
6. propagate each metric only to compatible ComponentTrackers;
7. create ComponentUsageEntry records;
8. mark the Session finalized.

The operation must be idempotent: retrying finalization must not duplicate usage.

## Circuit-derived usage

Circuit and CircuitLayout are separate concepts because a circuit may have multiple layouts. `CircuitLayout.length_meters` is authoritative.

Example:

- layout length: 1,250 m
- completed laps: 40
- generated distance: 50,000 m

The server calculates distance. The frontend must not be trusted to submit the final calculated value as authoritative.

## Manual usage

Manual usage on a configuration should create a UsageBatch and propagate that metric to compatible trackers on one explicit ConfigurationVersion. It must never update a raw `components.kilometers` field.

## Maintenance resets

A rebuild or service can reset a maintenance interval without erasing lifetime history. A TrackerResetEvent marks the point from which `since service` is calculated.

Example:

- lifetime runtime: 42.5 h
- runtime since last rebuild: 2.5 h

Both values remain derivable from the ledger.

## Future services

- `CreateConfigurationVersionService`
- `FinalizeSessionService`
- `UsagePropagationService`
- `RecordManualUsageService`
- `ComponentUsageCalculator`
- `MaintenanceService`

Business rules should live in services/actions rather than large Livewire components.

## Invariants

- historical sessions never resolve against a mutable current configuration;
- configuration versions referenced by finalized sessions are immutable;
- usage entries are append-only audit records;
- incompatible metrics are never propagated to a component;
- finalizing the same session twice cannot duplicate usage;
- service resets never delete lifetime usage;
- every future domain record is workspace-scoped even while the MVP has one personal workspace per user.
